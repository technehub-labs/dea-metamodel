CR-5 — Establish Assessment, Measurement & DMM Integration

| Field | Value |
|---|---|
| Status | Implemented (v0.10.0) |
| Depends on | CR-1, CR-2, CR-3, CR-4 |
Primary objective: Introduce a rigorous assessment and measurement ontology that allows DMMv5 and other maturity/assessment frameworks to assess the DEA semantic graph without becoming part of the DEA Core ontology.

This CR is particularly important because it establishes the architectural separation between:

What the enterprise is
How the enterprise is assessed
What evidence supports the assessment
What maturity means
Where the enterprise wants to be

These must not be conflated.

⸻

1. The fundamental correction

The model should explicitly establish:

DEA Architecture
       │
       │ is assessed by
       ↓
Assessment Framework
       │
       ├── Assessment Dimensions
       ├── Criteria
       ├── Indicators
       ├── Measures
       └── Maturity Model
                    │
                    ↓
              Assessment Result
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
       Score      Evidence   Confidence
          │
          ↓
       Baseline ───────→ Target

The architecture and the assessment are two different semantic layers.

⸻

2. Why this needs its own CR

A common metamodel anti-pattern is:

Capability
 ├── maturity = 3
 ├── maturity_target = 4
 ├── score = 72%
 └── assessment_date = ...

This is fundamentally wrong for a reusable DEA ontology.

A Capability does not intrinsically have a maturity score.

Rather:

AssessmentResult
       │
       └── assesses ──> Capability

and:

AssessmentResult
  ├── score
  ├── maturity level
  ├── evidence
  ├── confidence
  ├── assessor
  ├── framework
  └── assessment date

This allows the same Capability to be assessed:

* by DMMv5;
* by another maturity model;
* at different dates;
* against different criteria;
* at different organizational scopes;
* against different target states.

4. Assessment

Define:

Assessment is a structured evaluation of one or more subjects against an assessment framework at a defined point or period in time.

An Assessment should contain or reference:

assessment:
  id:
  framework:
  scope:
  subjects:
  started_at:
  completed_at:
  assessor:
  status:
  methodology:

Example:

Assessment A-2026-001
        │
        ├── framework → DMMv5
        ├── scope → Enterprise
        ├── period → 2026
        ├── assessor → AssessmentTeam
        └── assesses → Enterprise Architecture

⸻

5. Assessment Framework

AssessmentFramework represents the methodology used to conduct the assessment.

Examples:

DMMv5
Cybersecurity Maturity Model
AI Readiness Model
Data Maturity Model
Custom Enterprise Assessment

The framework must be external to the subject being assessed.

AssessmentFramework
        │
        └── defines ──> AssessmentCriterion

⸻

6. Assessment Dimension

A dimension is a structured perspective through which the subject is evaluated.

For DMMv5, the dimensions may include the established dimensions such as:

Strategy
Customer
Culture
Operations
Technology
Data

The important metamodel rule is:

A dimension is not an architectural entity merely because it is used to assess one.

Therefore:

DMM Dimension: Technology

does not become equivalent to:

DEA Entity: TechnologyComponent

The former is an assessment perspective.

The latter is an architectural element.

⸻

7. Assessment Criterion

A criterion defines what is being evaluated.

For example:

Dimension:
Technology
Criterion:
Technology Architecture Standardization

The criterion should contain:

id
name
definition
dimension
applicability
evaluation guidance

but should not contain the actual result.

⸻

8. Indicator

An Indicator defines the observable signal used to evaluate a criterion.

For example:

Criterion:
Technology Architecture Standardization
Indicator:
Percentage of strategic applications conforming
to the enterprise architecture standard.

This distinction is important:

Criterion = what we evaluate
Indicator = what we observe
Measure = what we quantify
Result = what was actually assessed

⸻

9. Measure

A Measure is the quantifiable observation.

For example:

measure:
  id:
  indicator: architecture-standardization
  value: 0.72
  unit: ratio
  observed_at: 2026-08-01
  source:

Other examples:

72 %
4.2 / 5
3.4 maturity points
18 months
USD 2.4M
125 applications

Do not encode the unit into the entity name.

⸻

10. Assessment Result

AssessmentResult is the central object connecting assessment to architecture.

Example:

assessment_result:
  id: AR-001
  assessment: A-2026-001
  subject: dea:capability/customer-management
  criterion: dmm:technology-standardization
  score:
    value: 3.2
    scale: dmm:5-level
  confidence:
    value: 0.84
  assessed_at: 2026-08-15

This allows:

AssessmentResult
       │
       ├── assessed-subject → Capability
       ├── criterion → DMM Criterion
       ├── measure → Measure
       ├── evidence → Evidence
       └── framework → DMMv5

⸻

11. Separate score from maturity

This distinction is critical.

A numerical score is not necessarily a maturity level.

For example:

Score = 72%

does not intrinsically mean:

Maturity Level = 4

The mapping between score and maturity must be defined by the assessment framework.

Therefore:

Measure
    ↓
Score
    ↓
Scoring Rule
    ↓
Maturity Level

The framework defines the transformation.

⸻

12. Maturity Model

Introduce:

MaturityModel
MaturityLevel
MaturityScale
MaturityRule

For example:

maturity_model:
  id: dmmv5:maturity
  levels:
    - id: 1
      name: Initial
    - id: 2
      name: Developing
    - id: 3
      name: Defined
    - id: 4
      name: Managed
    - id: 5
      name: Optimized

The actual DMMv5 terminology should be taken directly from the authoritative DMMv5 definition rather than invented by the metamodel.

⸻

13. Maturity belongs to the framework, not the entity

This is a key acceptance criterion.

Do not permit:

Capability:
  maturity: 4

Instead:

DMMv5
  │
  └── assesses
        │
        ↓
Capability
        │
        ↑
AssessmentResult
  │
  └── maturity-level → Level 4

This allows:

Capability A
  ├── DMMv5 → Level 3
  ├── AI Readiness Model → Level 2
  └── Internal Benchmark → Level 4

without conflict.

⸻

14. CR-5B — Establish Assessment Subject

A major improvement should be introducing an explicit AssessmentSubject.

The subject is the thing being evaluated.

It can reference:

Capability
Organization
BusinessFunction
Process
Service
Application
TechnologyComponent
DataEntity
Outcome
Architecture

Example:

assessment_subject:
  id:
  entity_ref: dea:capability/customer-management
  scope:
    organizational_unit: ...
    geography: ...
    business_unit: ...

This is particularly useful when the same entity exists at different scopes.

⸻

15. CR-5C — Establish assessment scope

Assessment must have explicit scope.

For example:

Scope
 ├── Enterprise
 ├── BusinessUnit
 ├── Capability
 ├── Domain
 ├── Geography
 ├── Product
 └── Program

But scope should be modeled as references to actual enterprise entities wherever possible.

For example:

Assessment
    │
    └── scope → Organization:RetailDivision

rather than:

scope = "Retail"

⸻

17. Evidence ≠ Assessment Result

This distinction must be explicit.

Example:

Evidence:
82% of applications have documented owners.
Assessment Result:
Technology governance maturity = Level 3.

The evidence supports the conclusion.

It is not the conclusion.

Therefore:

Evidence ──supports──> AssessmentResult

not:

Evidence = AssessmentResult

⸻

18. Evidence confidence

Add:

EvidenceConfidence
AssessmentConfidence

or a common confidence structure.

For example:

confidence:
  value: 0.87
  scale: 0..1
  rationale:

This becomes important later for AI-generated assessments.

⸻

19. Assessment provenance

Every result should answer:

Who assessed this, using what framework, when, based on what evidence?

Therefore:

AssessmentResult
 ├── assessment
 ├── subject
 ├── criterion
 ├── measure
 ├── evidence
 ├── assessor
 ├── assessed_at
 └── provenance

This should be mandatory for normative assessment results.

⸻

20. CR-5E — Baseline and Target State

This is one of the most important integrations with DEA transformation.

Do not encode:

Capability.maturity = 3
Capability.target_maturity = 5

Instead:

Baseline Assessment
        │
        ↓
Current State
        │
        ↓
Target Assessment
        │
        ↓
Target State

More formally:

AssessmentResult
      │
      ├── state-role → baseline
      │
      └── maturity → 2.8

and:

AssessmentTarget
      │
      ├── target maturity → 4.0
      ├── target date → 2028
      └── rationale

This makes maturity trajectory explicit.

⸻

21. Assessment Target

Create:

AssessmentTarget

with:

target:

  framework:
  criterion:

  target_level:
  target_date:
  rationale:

Target Date = 2028

⸻

22. CR-5F — Temporal assessment

Assessment is inherently temporal.

The same capability can evolve:

2024 → 2.1
2025 → 2.6
2026 → 3.2
2027 → 3.8

Therefore an assessment result must have:

valid_at
observed_at
assessed_at

where the distinctions matter.

For example:

* observed_at: when evidence was collected;
* assessed_at: when the assessment was performed;
* valid_from: when the result is considered applicable.

This lays the foundation for CR-6’s full temporal model.

⸻

23. CR-5G — DMM dimension mapping

DMM dimensions should map to DEA concepts rather than replace them.

For example:

DMM: Strategy
       │
       ├── assesses → Capability
       ├── assesses → Outcome
       └── assesses → Decision
DMM: Customer
       │
       ├── assesses → Service
       └── assesses → Outcome
DMM: Culture
       │
       ├── assesses → Actor
       ├── assesses → Organization
       └── assesses → Behavior
DMM: Operations
       │
       ├── assesses → Behavior
       ├── assesses → Capability
       └── assesses → Service
DMM: Technology
       │
       ├── assesses → TechnologyComponent
       ├── assesses → Application
       └── assesses → Service
DMM: Data
       │
       ├── assesses → Information
       └── assesses → DataEntity

This is a much stronger architectural relationship than creating six parallel “maturity pillars” inside the ontology.

25. CR-5H — Assessment aggregation

The metamodel must explicitly define how individual results become higher-level scores.

For example:

Criterion Results
       ↓
Dimension Score
       ↓
DMM Dimension Result
       ↓
Overall Assessment Result

Do not assume simple arithmetic averages.

Different frameworks may use:

* weighted averages;
* minimum thresholds;
* gating criteria;
* maturity ceilings;
* qualitative judgement;
* evidence sufficiency;
* rule-based scoring.

Therefore introduce:

AggregationRule
ScoringRule
MaturityMappingRule

⸻

26. Example

Suppose:

Technology dimension

contains:

Criterion A = 3.2
Criterion B = 2.8
Criterion C = 4.0

A naive model would calculate:

(3.2 + 2.8 + 4.0) / 3 = 3.33

But the framework may say:

If Criterion B < 3
then Technology maturity cannot exceed Level 2.

The metamodel must therefore support:

AssessmentResult
      │
      └── evaluated-by → AggregationRule

rather than hard-coding arithmetic into the ontology.

⸻

27. CR-5I — Assessment observations vs derived results

Separate:

Observation

Something measured or observed.

78% of applications have documented architecture.

Derived result

Interpretation:

Technology governance criterion = 3.4.

Maturity result

Framework interpretation:

Technology maturity = Level 3.

These are three different semantic objects.

Observation
    ↓
Measure
    ↓
Score
    ↓
AssessmentResult
    ↓
MaturityLevel

Some assessments may skip intermediate steps, but the metamodel should support the full chain.

⸻

28. CR-5J — Benchmarking

Benchmarking should be modeled separately from assessment.

Introduce:

Benchmark
BenchmarkPopulation
BenchmarkReference

Example:

Enterprise A = Level 3.2
Industry benchmark = Level 3.8
Peer median = Level 3.6
Strategic target = Level 4.2

These should not be conflated.

AssessmentResult ≠ Benchmark
AssessmentTarget ≠ Benchmark

⸻

29. CR-5K — Assessment maturity trajectory

The model should support:

baseline
current
target
forecast

For example:

2024     2025     2026     2027     2028
 │         │        │        │        │
 2.1      2.5      3.0      3.6      4.0
 │────────────────────────────────────→
              maturity trajectory

This is especially valuable for DMM because it converts an assessment from a static scorecard into a transformation trajectory.

⸻

30. CR-5L — Assessment gaps

Introduce a derived concept:

AssessmentGap

A gap exists between:

Current Result
       ↓
Target Result

Example:

gap:
  subject: Capability-X
  current: 2.7
  target: 4.0
  gap: 1.3
  target_date: 2028

But:

Gap should normally be derived, not authoritative source data.

The authoritative data are current state and target state.

⸻

31. CR-5M — Connect assessment to transformation

This is where DEA and DMM become particularly powerful.

AssessmentGap
      │
      └── addressed-by
              ↓
           Change
              │
              ├── affects → Capability
              ├── affects → Service
              ├── affects → Technology
              └── produces → Outcome

This creates a complete chain:

Assessment
    ↓
Current State
    ↓
Gap
    ↓
Required Change
    ↓
Target Architecture
    ↓
Outcome

That should become one of the signature capabilities of OpenDEA.

32. CR-5N — Don’t hard-code DMM into the assessment engine

DMMv5 should be an implementation of the generic assessment metamodel.

Conceptually:

Assessment Engine
      │
      ├── DMMv5
      ├── AI Readiness
      ├── Data Maturity
      ├── Cyber Maturity
      └── Custom Framework

All frameworks use:

Assessment
AssessmentFramework
Dimension
Criterion
Indicator
Measure
Evidence
Result
Target

but define their own:

* scoring;
* maturity;
* dimensions;
* criteria;
* aggregation;
* evidence requirements.

⸻

33. CR-5O — DMM versioning

DMM must be versioned independently from OpenDEA.

For example:

OpenDEA Core      1.0
Assessment Profile 1.0
DMMv5              5.x

A DMMv6 release should not require an OpenDEA Core release unless it changes the underlying DEA semantics.

This is another reason DMM must remain a profile.

⸻

34. CR-5P — Assessment framework interoperability

The model should permit multiple frameworks to assess the same subject.

Example:

Capability: Customer Management
       │
       ├── DMMv5 → 3.4
       ├── AI Readiness → 2.7
       ├── Data Maturity → 3.1
       └── Cyber Assessment → 4.0

This is an extremely powerful capability.

It means the enterprise has one architecture graph with multiple assessment lenses, rather than multiple disconnected maturity models.

⸻

36. CR-5R — Assessment conformance rules

Introduce automated rules:

A001

Every Assessment references exactly one AssessmentFramework.

A002

Every AssessmentResult references one valid subject.

A003

Every AssessmentResult references a valid criterion.

A004

Scores use a declared scale.

A005

Maturity levels belong to the referenced maturity model.

A006

Evidence references resolve to valid evidence objects.

A007

Assessment results cannot modify entity identity.

A008

Maturity cannot be stored as an intrinsic architectural attribute.

A009

Aggregation rules must be declared.

A010

Target values must identify their target date where temporal.

A011

Benchmark results cannot be treated as assessment results.

A012

Assessment framework versions are immutable once results reference them.

A013

A result cannot reference a deprecated criterion unless explicitly marked historical.

40. CR-5 acceptance criteria

CR-5 should not be accepted until:

* Assessment is explicitly separated from architecture.
* Assessment Framework is a first-class concept.
* Assessment Dimension is distinct from DEA entity.
* Assessment Criterion is distinct from Measure.
* Indicator and Measure are distinct.
* Assessment Result is distinct from Evidence.
* Evidence is first-class and supports provenance.
* Score and Maturity Level are distinct.
* Scoring and aggregation rules are explicit.
* Maturity models are independently versioned.
* Maturity is not an intrinsic property of DEA entities.
* Assessment Subject is explicitly modeled.
* Assessment Scope is explicitly modeled.
* Baseline and Target are separately represented.
* Assessment is temporally anchored.
* Confidence can be represented.
* Benchmarking is separated from assessment.
* Assessment gaps can be derived.
* Assessment gaps can connect to Change.
* DMMv5 is implemented as an assessment profile.
* DMM dimensions can assess multiple DEA entity types.
* Multiple assessment frameworks can assess the same DEA graph.
* Assessment framework versions are independently governed.
* Assessment conformance tests pass.
* Viewer can render assessment results as an overlay on the DEA graph.

41. Definition of Done

The decisive test is this:

Given a DEA entity:

Capability: Customer Management

the model must be able to answer:

What is it?
        ↓
Capability
How is it realized?
        ↓
Processes / Services / Applications
Who owns it?
        ↓
Organization
What outcome does it support?
        ↓
Outcome
How mature is it?
        ↓
NOT an intrinsic property
Which framework assessed it?
        ↓
DMMv5
When?
        ↓
Assessment date
Against what?
        ↓
Criterion
Based on what?
        ↓
Evidence
With what confidence?
        ↓
Confidence
What is the target?
        ↓
Target assessment
What is the gap?
        ↓
Derived AssessmentGap
What change addresses the gap?
        ↓
Change / Transformation

That is the desired semantic separation.

42. The resulting OpenDEA + DMM architecture

After CR-5, the overall model should look approximately like this:

                         ┌─────────────────┐
                         │    OpenDEA      │
                         │   Core Graph    │
                         └────────┬────────┘
                                  │
                    ┌─────────────┼─────────────┐
                    │             │             │
                    ↓             ↓             ↓
                Capability     Service       Information
                    │             │             │
                    └─────────────┼─────────────┘
                                  │
                            ASSESSMENT
                                  │
                     ┌────────────┴────────────┐
                     │                         │
                 Assessment                 Evidence
                     │
               ┌─────┴─────┐
               ↓           ↓
           DMMv5       Other Frameworks
               │
          ┌────┼─────┐
          ↓    ↓     ↓
      Dimension Criterion Measure
                     │
                     ↓
              AssessmentResult
                     │
              ┌──────┴──────┐
              ↓             ↓
          Current         Target
              │             │
              └──────┬──────┘
                     ↓
                AssessmentGap
                     │
                     ↓
                   Change
                     │
                     ↓
             Target Architecture
                     │
                     ↓
                   Outcome

This is the point where DEA stops being merely descriptive and becomes capable of supporting a closed loop:

Describe → Assess → Identify Gap → Decide → Transform → Measure → Reassess.

That closed loop should be one of the defining architectural characteristics of OpenDEA.

⸻

CR-6 should now address Time, State & Transition Architecture

With CR-5 in place, the next problem becomes unavoidable: the model can now describe current state, assessment results, targets and changes, but it needs a rigorous temporal semantics to distinguish:

current architecture → baseline → transition state → target architecture → realized state, including effective dates, supersession, validity, planned changes and historical assessments.

I would therefore make CR-6 — Temporal, Lifecycle & Transition Semantics the next CR, before introducing the more sophisticated Decision/Agentic Architecture in CR-7.
