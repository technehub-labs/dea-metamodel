CR-7 — Decision, Intent, Policy, Governance & Agentic Semantics

| Field | Value |
|---|---|
| Status | Implemented (v0.12.0) |
| Depends on | CR-1 through CR-6 |
Primary objective: Establish the semantic foundation for intent-driven, governed, decision-centric and agentic enterprise architecture.

CR-1–CR-6 progressively establish:

CR-1  → Core semantic foundation
CR-2  → Relationships and graph semantics
CR-3  → Architectural domains / composition
CR-4  → Conformance and semantic integrity
CR-5  → Assessment, measurement and DMM integration
CR-6  → Time, state, lifecycle and transition

CR-7 should now add the missing causal/governance layer:

                    INTENT
                       │
                       ↓
                    POLICY
                       │
                       ↓
                    DECISION
                       │
            ┌──────────┼──────────┐
            ↓          ↓          ↓
        Action       Change     Constraint
            │          │          │
            └──────────┼──────────┘
                       ↓
                 Architecture
                       │
                       ↓
                    Outcome
                       │
                       ↓
                   Evidence
                       │
                       ↓
                  Reassessment

The critical architectural principle is:

An Agent is not the center of the metamodel. Decision, intent, authority, policy, evidence, action and accountability are. Agents are participants in that semantic system.

⸻

1. Why CR-7 is necessary

After CR-6, OpenDEA can represent:

what exists, how mature it is, when it exists, how it changes, and what the target state is.

But it still needs to represent:

why a change is desired, who has authority to decide it, what constraints govern it, what evidence informs it, what action follows from the decision, and whether an autonomous agent can participate in that process.

Without this, “agentic enterprise architecture” risks becoming:

Agent
 ├── name
 ├── description
 ├── model
 └── tools

That is an agent inventory, not an agentic enterprise architecture.

⸻

The core pattern should be:

  ↓

  ↓

  ↓

  ↓

This creates a closed-loop enterprise model:

Intent → Decision → Action → Change → Outcome → Evidence → Learning → Decision

This should become one of the defining characteristics of OpenDEA.

3. CR-7A — Establish Intent

Create:

Intent
Objective
DesiredOutcome

An Intent expresses the desired direction or purpose behind an architectural or organizational decision.

Examples:

Reduce operational cost
Improve customer experience
Increase resilience
Become AI-enabled
Reduce technology complexity
Improve regulatory compliance
Increase data interoperability

Intent is not a goal metric.

For example:

Intent:
Improve customer experience
Objective:
Reduce average customer resolution time to < 2 minutes
Outcome:
Customer resolution time = 1.7 minutes

These must remain distinct.

⸻

4. Intent hierarchy

Support composition:

Enterprise Intent
       ↓
Strategic Intent
       ↓
Business Objective
       ↓
Transformation Objective
       ↓
Operational Objective

But do not force a universal hierarchy.

The important semantics are:

Intent
   ├── motivates → Objective
   ├── constrained-by → Policy
   └── seeks → Outcome

⸻

5. CR-7B — Objective

Introduce:

Objective

An objective makes an intent operationally measurable.

Example:

objective:
  id: OBJ-001
  intent: improve-customer-experience
  statement: reduce customer resolution time
  target_value: 120
  unit: seconds
  target_date: 2027-12-31

This connects naturally with CR-5:

Objective
    ↓
Target
    ↓
Assessment

⸻

6. Objective ≠ Outcome

This distinction is essential.

Objective:
What we intend to achieve.
Outcome:
What actually happened.

Example:

Objective:
Reduce resolution time to 120 seconds.
Outcome:
Resolution time achieved = 103 seconds.

This gives the architecture a measurable causal loop.

⸻

7. CR-7C — Policy

Introduce:

Policy
PolicyRule
PolicyConstraint

A policy represents a governing principle or rule that constrains or directs behavior.

Examples:

All customer data must remain within approved jurisdictions.
Production AI agents must have human override capability.
Critical architecture decisions require Architecture Board approval.
No system may process PII without an approved data classification.
Technology components must use approved standards.

A policy can apply to:

9. CR-7D — Constraints

Policy and constraint should not be conflated.

A constraint is a condition that limits what is possible or permissible.

Examples:

Budget ≤ $10M
Deployment must complete by June 2027
System must achieve 99.99% availability
Agent cannot approve payments above $50,000
Architecture must comply with regulation X

Model:

Constraint
   │
   ├── constrains → Decision
   ├── constrains → Action
   ├── constrains → Change
   └── constrains → Architecture

⸻

10. Hard vs soft constraints

Support explicit constraint strength:

Hard Constraint
Soft Constraint
Preference
Guideline

Example:

Hard:
Must comply with regulation.
Soft:
Prefer cloud-native implementation.
Preference:
Prefer vendor-neutral technology.

This becomes important for automated decision-making.

11. CR-7E — Decision as a first-class concept

Create:

Decision
DecisionOption
DecisionCriteria
DecisionOutcome
DecisionRationale
DecisionRecord

A Decision should capture:

who/what decided
what was decided
why
based on what evidence
under what authority
subject to which policies
among which alternatives
with what consequences

Example:

decision:
  id: DEC-2026-042
  statement: adopt federated data architecture
  decision_maker: ArchitectureBoard
  authority: EnterpriseArchitecturePolicy
  intent: improve-data-interoperability
  evidence:
  - assessment-result-001
  options:
  - centralized
  - federated
  - hybrid
  selected_option: federated
  rationale: ...

⸻

12. Decision ≠ Change

This distinction is fundamental.

Decision:
"We will implement federated data architecture."
Change:
"Implement the federated data architecture."

The decision authorizes or directs a change.

It does not constitute the change itself.

Decision
   ↓ authorizes / directs
Change

⸻

13. Decision ≠ Action

Likewise:

Decision:
Approve migration.
Action:
Execute migration.

A Decision may result in one or more Actions.

Decision
   ↓
Action 1
Action 2
Action 3

14. CR-7F — Decision alternatives

Every meaningful decision should be capable of representing alternatives.

 ├── Option C

expected outcome

This makes architecture decision-making explicit rather than burying rationale in documents.

18. CR-7H — Authority

Introduce:

Authority
DecisionAuthority
Delegation

A critical principle:

Capability to perform an action is not the same as authority to perform it.

For example:

Agent A
   ├── capability → approve transaction
   └── authority → NOT authorized above $10,000

This distinction should be structurally represented.

20. CR-7I — Agent

Now introduce the Agent.

But the definition should be deliberately broader than “AI model”.

Define:

Agent = an autonomous or semi-autonomous actor capable of perceiving information, reasoning or evaluating conditions, and initiating or executing actions within a defined authority and policy boundary.

This allows:

Human Agent
Organizational Agent
Software Agent
AI Agent
Autonomous System
Composite Agent

23. CR-7K — Agent autonomy

Do not use a simple:

autonomous = true/false

Use an explicit autonomy model.

For example:

Level 0 — Inform
Level 1 — Recommend
Level 2 — Prepare
Level 3 — Execute with approval
Level 4 — Execute within delegated authority
Level 5 — Autonomous

The exact levels should remain configurable.

The metamodel should model:

AutonomyPolicy
AutonomyLevel
HumanOversight
ApprovalRequirement

rather than hard-coding a particular scale.

24. Agent action boundary

An agent should have an explicit action boundary.

Example:

Agent:
Customer Service Agent
Can:
- retrieve customer information
- summarize cases
- create service tickets
- recommend resolutions
Cannot:
- change customer identity
- approve refunds > $500
- modify pricing
- delete customer records

This should be represented through:

Agent
   ├── permitted-action
   ├── prohibited-action
   └── requires-approval

27. CR-7N — Agent as an enterprise actor

 ├── Role
 ├── Agent
 └── System

31. Tool ≠ Service

Do not collapse them.

A Service represents an enterprise capability exposed for consumption.

A Tool represents an executable mechanism an actor/agent can invoke.

They can overlap operationally but have different semantics.

46. CR-7Z — Agentic orchestration

This is where the distinction between Controller, Orchestrator and Agent should become explicit.

Agent

Performs a bounded cognitive/action role.

Orchestrator

Coordinates multiple actors/actions toward a goal.

Controller

Enforces execution/state/control conditions.

Conceptually:

Orchestrator
   │
   ├── invokes → Agent A
   ├── invokes → Agent B
   ├── invokes → Service
   └── coordinates → Workflow

while:

Controller
   │
   ├── enforces → Policy
   ├── evaluates → State
   ├── controls → Execution
   └── triggers → Escalation

Do not collapse these into a generic Agent.

62. CR-7AN — Conformance rules

Introduce at least these rules.

G001 — Decision authority

Every governed Decision must reference an authorized decision maker.

G002 — Decision evidence

Material Decisions must identify their supporting evidence or rationale.

G003 — Decision/change separation

A Decision cannot itself be interpreted as an implemented Change.

G004 — Policy applicability

A Policy must identify its scope/applicability.

G005 — Delegated authority

Delegated authority must have explicit scope and validity.

G006 — Agent authority

Every operational Agent must have defined authority.

G007 — Agent ownership

Every production Agent must have an accountable owner.

G008 — Agent policy

Every production Agent must reference applicable governance policies.

G009 — Tool permission

Agent tool access must be governed by explicit permission/authority.

G010 — Autonomous action

Autonomous actions must be within delegated authority.

G011 — Human escalation

Actions exceeding an Agent’s authority must escalate or fail safely.

G012 — Risk controls

High-risk autonomous actions must reference appropriate controls.

G013 — Agent lifecycle

Production Agents must have lifecycle state.

G014 — Skill validity

An Agent cannot invoke a Skill outside its granted capability/authority.

G015 — Scenario isolation

Hypothetical agents cannot appear as active production agents.

G016 — Accountability

Every material automated decision must have an accountable party.

65. The most important CR-7 architectural rule

I would make this an explicit principle in the repository:

Agentic semantics must reuse the core DEA semantics wherever the underlying concept is already represented.

Therefore:

Agent Decision

should normally be:

Decision
   +
made-by → Agent

not a separate:

AgentDecision

Similarly:

Agent Action

should normally be:

Action
   +
performed-by → Agent

not:

AgentAction

And:

Agent Outcome

should be:

Outcome
   +
realized-by → AgenticSystem

This keeps the metamodel coherent.

66. What CR-7 deliberately does NOT do

CR-7 should not attempt to fully specify:

* LLM architecture;
* prompt formats;
* vector databases;
* RAG implementation;
* model training;
* tokenization;
* inference parameters;
* vendor-specific agent frameworks;
* MCP implementation details;
* LangChain/CrewAI/etc. abstractions;
* individual AI model architectures.

Those belong in implementation or technology-specific profiles.

The DEA metamodel should describe enterprise semantics, not become an AI engineering framework.

67. CR-7 Definition of Done

CR-7 is complete when OpenDEA can answer:

Intent

Why does this architecture/change exist?

Objective

What are we trying to achieve?

Governance

What policies constrain it?

Authority

Who is authorized to decide or act?

Decision

What was decided and why?

Evidence

What informed the decision?

Agent

Which human, system or autonomous agent performs the work?

Autonomy

How much authority does it have?

Action

What can it actually do?

Governance

What happens when it exceeds its authority?

Change

What architecture does the action alter?

State

What architecture state does it create?

Outcome

What business result does it produce?

Assessment

Did the result improve the enterprise?

Learning

What evidence feeds the next decision?

If the graph can answer all of these without relying on undocumented external semantics, CR-7 has achieved its objective.
