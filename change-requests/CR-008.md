CR-8 — OpenDEA Semantic Architecture & Conformance Specification

| Field | Value |
|---|---|
| Status | Implemented (v1.0.0) |
| Depends on | CR-1 through CR-7 |
| Type | Foundational consolidation / standardization |
Primary objective: Transform the accumulated OpenDEA metamodel into a formal, machine-validatable, profile-driven semantic specification with deterministic conformance rules and a reference implementation.

CR-8 is not another expansion of the metamodel. It is the consolidation phase that turns the metamodel into a specification.

⸻

1. Purpose

CR-1 through CR-7 progressively establish the conceptual foundations:

CR-1  Core semantic foundation
CR-2  Relationships and graph semantics
CR-3  Architecture domains and composition
CR-4  Conformance and semantic integrity
CR-5  Assessment and measurement
CR-6  Time, state and lifecycle
CR-7  Intent, decision, governance and agentic semantics

CR-8 now answers:

Exactly what does it mean for a DEA model to be OpenDEA-conformant?

It should establish:

Semantic vocabulary
        ↓
Canonical metamodel
        ↓
Type system
        ↓
Relationship system
        ↓
Constraints
        ↓
Profiles
        ↓
Machine-readable schema
        ↓
Validation engine
        ↓
Conformance tests
        ↓
Reference examples

2. CR-8 design principle

The most important principle is:

Separate the semantic core from profiles, implementation schemas and visualization.

The architecture should become:

                    OpenDEA
                       │
             ┌─────────┴─────────┐
             ↓                   ↓
        DEA Core              Profiles
             │                   │
             │       ┌───────────┼───────────┐
             │       ↓           ↓           ↓
             │      DMM       Agentic     Governance
             │
             ↓
       Serialization
             │
       ┌─────┼─────┐
       ↓     ↓     ↓
     YAML   JSON   RDF/OWL*
             │
             ↓
        Validation
             │
             ↓
        Conformance

RDF/OWL should be evaluated as an interoperability representation rather than automatically made mandatory.

4. Do not allow Core inflation

CR-8 should explicitly define a rule:

A concept belongs in Core only if removing it would make the general DEA semantic system incomplete.

For example:

Agent

may belong in Core if OpenDEA’s fundamental proposition includes autonomous actors.

But:

Prompt
Embedding
VectorStore
LLMTemperature
TokenBudget

do not.

Those belong in an Agentic/AI implementation profile.

5. CR-8B — Canonical vocabulary

Create the authoritative OpenDEA vocabulary.

Every concept receives:

id:
name:
canonical_name:
definition:
description:
semantic_category:
parent:
abstract:
status:
version:

Example:

id: decision
name: Decision
canonical_name: Decision
definition: >
  A determination made by an authorized actor that selects
  a course of action from one or more alternatives.

abstract: false
status: stable

There must be one canonical definition per semantic concept.

7. CR-8C — Concept identity

This is critical.

Names are not identities.

For example:

"Customer Service"

could refer to:

* a capability;
* an organizational function;
* a service;
* a department;
* a process.

Therefore every modeled object needs a stable identity.

id: capability.customer-service
type: BusinessCapability
name: Customer Service

The id must remain stable even if the display name changes.

Define the OpenDEA type system formally.

At minimum:

 ├── GovernanceElement
 ├── AssessmentElement
 └── AgenticElement

But avoid excessive inheritance.

Prefer:

type
+

+

9. CR-8E — Abstract vs concrete concepts

Every class must declare whether it is:

  abstract: true

  abstract: false

This prevents models from instantiating semantic placeholders incorrectly.

11. Relationship semantics

Every relationship should define:

relationship:
  id:
  source:
  target:
  inverse:
  cardinality:
  transitive:
  symmetric:
  temporal:
  description:

Example:

relationship:
  id: implements
  source: ArchitectureElement
  target: Requirement
  inverse: implementedBy
  cardinality: 0..*
  transitive: false
  symmetric: false

⸻

12. CR-8G — Relationship direction

The repository should enforce a canonical direction.

For example:

Capability
    └── supportedBy → Service

should not randomly appear elsewhere as:

Service
    └── supports → Capability

unless the inverse relationship is explicitly defined.

Both may be queryable:

supports
inverseOf supportedBy

but only one is canonical.

This eliminates graph ambiguity.

⸻

13. CR-8H — Cardinality

Every relationship needs cardinality.

Examples:

1
0..1
1..*
0..*

Example:

Agent
   owner → Actor

could be:

Agent.owner = 1

while:

Agent
   uses → Tool

could be:

0..*

This should be machine validated.

⸻

14. CR-8I — Composition vs reference

This distinction should become formal.

Composition

The child has no independent lifecycle from the parent.

AgentProfile
   └── AgentPolicy

Reference

Both entities have independent identities/lifecycles.

Agent
   └── governedBy → Policy

Do not represent both using generic nesting.

This will significantly improve model integrity.

⸻

15. CR-8J — Inheritance vs specialization

The model should distinguish:

isA

from:

specializes

and:

implements

Example:

AI Agent
   isA → Agent

whereas:

Customer Service Agent
   specializes → Agent

and:

Agent
   implements → Capability

These must not become interchangeable relationship types.

⸻

16. CR-8K — Profiles

Profiles become one of the most important CR-8 concepts.

The Core should be extensible through profiles:

OpenDEA Core
     │
     ├── DMM Profile
     ├── Governance Profile
     ├── Agentic Profile
     ├── Security Profile
     ├── Data Architecture Profile
     ├── Technology Architecture Profile
     └── Industry Profiles

A profile may:

add concepts
add relationships
add properties
add constraints
specialize concepts
define enumerations
define assessment dimensions

but must not silently redefine Core semantics.

⸻

17. Profile conformance

A model should be able to declare:

profiles:
  - opendea-core@1.0
  - opendea-dmm@1.0
  - opendea-agentic@1.0

The validator then knows exactly which semantic extensions apply.

⸻

18. CR-8L — Versioning

CR-8 should introduce formal semantic versioning.

Recommended:

MAJOR.MINOR.PATCH

MAJOR

Breaking semantic changes.

MINOR

Backward-compatible additions.

PATCH

Corrections without semantic change.

Example:

OpenDEA Core 1.4.2

⸻

19. Semantic compatibility

A particularly important rule:

A schema can remain syntactically compatible while becoming semantically incompatible.

Therefore compatibility must be evaluated at two levels:

Syntax compatibility
+
Semantic compatibility

Example:

Changing:

supports

from:

Capability enables Service

to:

Service enables Capability

is a semantic breaking change even if the JSON schema remains valid.

⸻

21. CR-8N — Machine-readable schema

The repository should generate a canonical machine-readable representation.

At minimum:

JSON Schema

and preferably also:

JSON-LD context

if RDF/semantic-web interoperability is part of the roadmap.

The JSON representation should not become the semantic definition itself.

Instead:

Canonical semantic specification
            ↓
     Schema generation
            ↓
 JSON Schema / JSON-LD / etc.

This prevents the schema from becoming the accidental ontology.

25. CR-8R — Constraints language

CR-8 should establish a machine-readable constraint mechanism.

At minimum:

Required property
Cardinality
Type compatibility
Relationship validity
Enumeration
Uniqueness
Conditional rule
Cross-object rule

For example:

IF Agent.autonomyLevel >= 4
THEN Agent.authority MUST exist
AND Agent.accountableOwner MUST exist
AND Agent.governancePolicy MUST exist

This is considerably more powerful than basic JSON schema validation.

26. CR-8S — SHACL-style graph validation

If OpenDEA adopts RDF/JSON-LD semantics, evaluate SHACL for graph-level validation.

The important architectural distinction is:

JSON Schema
    ↓
Document structure
Graph constraints
    ↓
Semantic integrity

For example:

Every Capability must be owned by an organizational context.

That cannot always be adequately expressed through simple document structure.

27. CR-8T — Conformance levels

Create explicit conformance levels.

Level 0 — Syntax

Document parses.

Level 1 — Structural

Schema is valid.

Level 2 — Semantic

Types and relationships are valid.

Level 3 — Profile

Declared profiles are conformant.

Level 4 — Governance

Required governance and accountability semantics exist.

Level 5 — Operational

Lifecycle, assessment and execution semantics are valid.

Potentially:

OpenDEA Conformance
       │
       ├── Core
       ├── Profile
       ├── Governance
       ├── Agentic
       └── Assessment

Do not make an organization claim “OpenDEA compliant” without specifying the level/profile.

38. CR-8AE — Derived relationships

Some relationships should be inferable.

Example:

Agent
 → uses Tool
 → invokes Service
 → supports Capability

Therefore:

Agent
 → indirectly supports Capability

The system should distinguish:

explicit relationship

from:

inferred relationship

Never write inferred relationships back into the authoritative model unless explicitly requested.

55. CR-8AV — Avoid “mega-model” failure

A major warning for the next phase:

Do not solve extensibility by putting every possible enterprise concept into Core.

The failure pattern would be:

Core
 ├── Finance
 ├── Healthcare
 ├── AI
 ├── Manufacturing
 ├── Cybersecurity
 ├── HR
 ├── Marketing
 ├── IoT
 ├── Sustainability
 └── ...

That would eventually produce an unmanageable ontology.

The correct pattern is:

Small stable Core
       +
Composable Profiles
       +
Explicit mappings

⸻

56. CR-8AW — Formal semantic invariants

CR-8 should define invariants that must always hold.

Examples:

Identity

Every concrete entity MUST have a unique identifier.

Type

Every entity MUST have exactly one canonical primary type.

Relationship

Every relationship MUST reference a declared relationship type.

Lifecycle

Every lifecycle-managed entity MUST have a valid lifecycle state.

Governance

Every autonomous production Agent MUST have authority and accountability.

Assessment

Every AssessmentResult MUST reference an Assessment context.

These become the mathematical/semantic contract of OpenDEA.

⸻

57. CR-8AX — Open-world vs closed-world semantics

This needs explicit treatment.

For ordinary architecture modeling:

Absence of a relationship does not necessarily mean the relationship does not exist.

Therefore Core should generally behave under open-world assumptions.

However, validation rules may impose closed-world requirements within specific profiles.

Example:

Core:
Agent has no declared policy.
→ Unknown.
Governance Profile:
Production Agent has no declared policy.
→ Non-conformant.

This distinction is subtle but extremely important.

⸻

67. CR-8BH — Most important correction to the project

I would make this an explicit architectural decision:

The GitHub repository must not simultaneously act as the conceptual model, schema, viewer data structure, visualization model, documentation model and application runtime model.

Those concerns should be separated.

The dependency direction should be:

              OPENDEA SEMANTIC SPECIFICATION
                            │
                ┌───────────┼───────────┐
                ↓           ↓           ↓
             Schema      Validator    Profiles
                │                       │
                └───────────┬───────────┘
                            ↓
                       Reference Model
                            │
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
           Viewer          API          AI Agents

Never reverse this dependency.

The viewer should not define the model.

The JSON structure should not accidentally define the semantics.

The AI agent should not define the ontology.
