CR-11 — Interoperability, Federation & Ecosystem Conformance

Status: Proposed
Predecessors: CR-1 → CR-10
Primary objective: Make OpenDEA interoperable with external enterprise-architecture, data, governance, assessment, operational, and AI ecosystems without allowing external formats or standards to distort the OpenDEA canonical semantic model.

⸻

1. Why CR-11 is the next logical phase

CR-10 established the ability to represent:

Current State
Target State
Scenario
Impact
Outcome
Decision
Simulation
Transformation

The next problem is:

How does OpenDEA exchange this knowledge with the outside world?

Enterprise architecture data rarely originates in one system.

It will typically exist across:

EA repositories
CMDBs
Data catalogs
Application portfolios
ITSM platforms
GRC platforms
DMM assessments
Project/portfolio systems
Cloud platforms
Business process repositories
HR systems
AI/agent registries
Operational systems
External standards

Therefore, OpenDEA needs a formal interoperability architecture.

The critical design principle is:

OpenDEA should be the semantic contract; adapters should absorb external complexity.

⸻

2. CR-11 architectural principle

Do not build this:

External System A
       ↓
OpenDEA
       ↑
External System B
       ↓
OpenDEA
       ↑
External System C

where each integration modifies the core model.

Instead:

                         OPENDEA
                    Canonical Semantic
                         Model
                            │
             ┌──────────────┼──────────────┐
             ↓              ↓              ↓
        Adapter A      Adapter B      Adapter C
             ↓              ↓              ↓
          System A       System B       System C

The OpenDEA core remains stable.

⸻

3. CR-11A — Formal Interoperability Model

Introduce four distinct concepts:

Source
Adapter
Mapping
Exchange

Source

An external system or artifact.

Adapter

Technical mechanism for accessing it.

Mapping

Semantic correspondence between external and OpenDEA concepts.

Exchange

The actual transfer of information.

Do not conflate these.

   ↓

   ↓

   ↓

   ↓

This distinction will prevent integration architecture from becoming confused with semantic interoperability.

15. CR-11M — Source authority

This is one of the most important CR-11 concepts.

Different sources should have different authority for different facts.

Example:

CMDB
→ operational configuration
EA Repository
→ architecture classification
HR
→ organizational ownership
GRC
→ control/compliance status
DMM
→ maturity assessment

Therefore authority should be property-specific, not simply:

System A = trusted
System B = untrusted

⸻

16. CR-11N — Authority policy

Introduce:

AuthorityPolicy

Example:

property: application.operationalStatus

  - CMDB: 100
  - EARepository: 60

Whereas:

property: application.architectureClassification
authority:
  - EARepository: 100
  - CMDB: 40

This is much more powerful than a global source hierarchy.

66. One correction I would make to the overall CR strategy

There is a subtle but important architectural risk now that CR-1 through CR-11 are assembled:

Do not allow the metamodel to become an accumulation of every concept the platform touches.

The Core should remain something closer to:

                 OPENDEA CORE
                      │
      ┌───────────────┼────────────────┐
      ↓               ↓                ↓
   Identity       Semantics         State
      │               │                │
      ↓               ↓                ↓
 Entities       Relationships      Assertions
 Profiles       Constraints        Evidence
                                       │
                                       ↓
                                  Provenance

Then everything else should sit above or beside it:

                    APPLICATIONS
                         │
       ┌─────────────────┼─────────────────┐
       ↓                 ↓                 ↓
      DMM              AI/Agents       Scenarios
       │                 │                 │
       └─────────────────┼─────────────────┘
                         ↓
                    OPENDEA RUNTIME
                         │
                         ↓
                   OPENDEA CORE
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
     ArchiMate          BPMN             CMDB
     DMN                GRC              Data

That distinction is what will allow OpenDEA to become an ecosystem and semantic standard rather than merely a very sophisticated application schema.

⸻

CR-11’s strategic outcome

After CR-11, the architecture should be able to make this claim credibly:

OpenDEA provides a canonical semantic layer through which heterogeneous enterprise knowledge, architecture models, assessments, operational information, scenarios, decisions, and agentic capabilities can interoperate without requiring those external systems to adopt the OpenDEA metamodel.

That is a significantly stronger position than simply saying that OpenDEA “supports integrations.”

And it establishes the correct foundation for CR-12: Enterprise Intelligence, Agentic Reasoning & Governed Autonomous Operations—where the focus shifts from connecting enterprise knowledge to using that connected knowledge to continuously reason, recommend, coordinate, and act.
