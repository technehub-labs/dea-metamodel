## 1. Context

ADR-015 (2026-08-31) decides that capability kinds are expressed by
specialization of an abstract root, not by classifier entities, not by
ECF coordinates, and not by compound typing. This CR implements that
decision.

The metamodel currently has no `parent` field on entities. Type-level
specialization is expressed through the `dea:specializes` structural
relationship, whose source and target type lists are closed enumerations
declared in two places: the relationship definition in
`metamodel/dea-metamodel.yaml` and the registry copy in
`metamodel/registry/relationships.yaml`. Both must be extended.

The capability instance schema (`schemas/entities/capability.json`)
already carries a free-form `capability_type` string and a `domain`
field. The free-form `capability_type` predates this classification
discipline and must be reconciled with typing-by-specialization.

The Core freeze (CR-8) and anti-accumulation rule (ADR-013) constrain
this change: the Core gains exactly one abstract anchor. All concrete
kind specializations live in profiles (ADR-002).

## 2. Changes

### 2.1 Core: abstract `dea:Capability`

Add to `metamodel/core/core-entities.yaml` and
`metamodel/dea-metamodel.yaml`:

```yaml
- id: dea:Capability
  name: Capability
  legacy_ids: []
  definition: An attributable, contextualized potential of an Entity to
    accomplish a defined kind of effect, grounded in capacity and ability
    within a defined context. Aligned 1:1 with wsf:Capability
    (ADR-WSF-07).
  layer: null
  dimension: null
  building_block: null
  abstract: true
  status: normative
  lifecycle: planned
  class_alias: null
  catalog_repo: null
  membership:
    kind: core
    profile: null
```

### 2.2 `dea:BusinessCapability` becomes a specialization

- Definition retained verbatim; append: "Specializes `dea:Capability`
  (ADR-015): contributes to a business outcome, owned by the business,
  mapped to ECF coordinates."
- The legacy alias `Capability` migrates from
  `dea:BusinessCapability.legacy_ids` to `dea:Capability.legacy_ids`
  (the generic name now denotes the root). `dea:entity-capability`
  remains on `dea:BusinessCapability`.
- A type-level `specializes` edge `dea:BusinessCapability →
  dea:Capability` is declared following the existing APC/IFC/IGC
  pattern (ADR-0002 D3).

### 2.3 Profile-level kind specializations

Three new entities, each defined as parent meaning plus additional
constraints (ADR-WSF-04); none redefines capability semantics:

| Entity | Profile | Additional constraint |
|--------|---------|----------------------|
| `dea:SystemCapability` | `dea:technology` | Bearer is a system or application; enables a system function |
| `dea:InfrastructureCapability` | `dea:technology` | Bearer is infrastructure; enables platform or runtime services |
| `dea:AIAugmentedCapability` | `dea:ai` | Realisation depends on a model or agent; subject to the AI & Automation Governance dimension |

Each entry is declared in its profile YAML with `membership.kind:
profile`, `abstract: false`, `lifecycle: proposed`, and a type-level
`specializes` edge to `dea:Capability`.

### 2.4 Relationship vocabulary extension

Extend the closed type lists of `dea:specializes` in both
`metamodel/dea-metamodel.yaml` and `metamodel/registry/relationships.yaml`:

- source types: add `dea:BusinessCapability` (already present), and the
  three new kinds; add `dea:Capability` to allow future kind nesting
- target types: add `dea:Capability`

### 2.5 Capability schema: governed layer attribute

In `schemas/entities/capability.json`:

- Add `capability_layer`: governed enumeration
  `strategic | operational | support`, optional, default unset.
- Deprecate free-form `capability_type`: retain for backwards
  compatibility, mark `deprecated: true`, and document that kind is now
  expressed by the entity type (specialization), not by a string field.
- `domain` (ECF coordinate metadata) is unchanged and remains
  classification metadata, never a kind classifier (ADR-015 §6).

### 2.6 WSF federation mapping

Add `mappings/wsf/mapping.yaml` declaring:

- `dea:Capability` ↔ `wsf:Capability` (exact, 1:1)
- `dea:BusinessCapability` ↔ `odea:BusinessCapability` (exact, as
  published in `wsf/concepts/capability.md`)
- `dea:SystemCapability`, `dea:InfrastructureCapability`,
  `dea:AIAugmentedCapability` ↔ specializations of `wsf:Capability`
  (narrower, lossiness: none declared at introduction)

### 2.7 Regeneration

Run the existing generators (`.github/scripts/`): registry, JSON schema
validation, Pydantic models, TypeScript interfaces, entity graph,
specification. All diffs must trace to sections 2.1 to 2.6.

## 3. Acceptance criteria

1. `dea:Capability` validates as an abstract Core entity; Core concrete
   anchor count unchanged (CR-8 freeze holds).
2. `dea:BusinessCapability` carries a `specializes` edge to
   `dea:Capability`; its definition text is otherwise byte-identical.
3. All three new kinds validate in their profiles and each carries a
   `specializes` edge to `dea:Capability`.
4. `dea:specializes` type lists in both files admit exactly the new
   source/target additions; `validate_metamodel_yaml.py` and
   `validate_json_schemas.py` pass.
5. `capability.json` accepts `capability_layer` values only from the
   governed enumeration; a payload with an out-of-vocabulary layer fails
   validation.
6. `mappings/wsf/mapping.yaml` passes the cross-repo validator.
7. Regenerated artifacts diff clean against sections 2.1 to 2.6; CI
   green.

## 4. Risks and mitigations

| Risk | Mitigation |
|------|-----------|
| Existing catalog instances carry free-form `capability_type` values | Field deprecated, not removed; values preserved; migration guidance deferred to a catalog-side CR |
| `dea:specializes` type-list drift between the two declaration sites | Single PR touches both; CI validators assert consistency |
| Future pressure to add kinds to the Core | ADR-015 §4 and ADR-013 cited in the entity definitions themselves |
